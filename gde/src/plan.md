So if we import a video file then it will hold that video, along with stuff like the duration, frame rate, start offset, etc. Then we can have a Clip node in the UI which contains a clip, and it will show in the timeline and you can click it to select that clip, or drag it to reposition it in the timeline.

The timeline will work in frames, we don't want to be able to position clips at sub frame positions, but we can only import one video file in a project anyway, and it will be unmovable, so it's not a big problem? We want to store the offset as a float or maybe as samples? Because you're supposed to be able to drag audio clips as well and those can be positioned at sub frame positions
The project sample rate is the lowest granularity for the entire project, there's no unit smaller than one sample. When we import a video, it sets it as the active video clip, sets the project's sample rate to the converted sample rate (1920x1080x30x3 for example). When we convert to samples for working, we take a frame of data from the timeline, all the frames from those clips get converted to the sample rate, and they get sent into the processor, then reassembled into their frames on the other end (only the video needs to get reassembled since we don't allow audio processing in the program), the audio chunks can be discarded.

So when we want to process a frame, we take the current frame index like 100, and the video clip converts itself to samples by turning every pixel in its frame into a byte array, we then also calculate all the audio samples from the rest of the clips that fall within that frame, and we send all that data to the processor. So we get all the data from that one frame from all the clips as one contained chunk of data to be processed.

So we have clips, they can be video or audio, have a start time and duration, and they can extract a chunk of data from themselves to give to something else.
The timeline is a container for clips, it handles playback position, looping, all of that stuff, it probably is mostly gdscript because it shouldn't be too performance intensive? Unless we hit a hotpath.
Signals are the data structure for processing, when a clip converts itself to a chunk of data, we create a signal containing the byte array, the timestampm, and other relevant metadata like what clip it came from, its name, etc.
The processor is a container for the nodes, it takes in signals, processes them through the nodes, and outputs the final result signals.
The nodes are the processing units, they take in signals, do some processing on them, and output the resulting signals. I assume we want to do something like in-place processing instead of copying because the signals might be very large.

Here's a problem, we need to have the pre-samples and post-samples along with the samples, because we need to warm up the processor with state sometimes before we can get the actual valid samples for the frame we want, so something needs to be orchestrating that, the processor itself doesn't really care, it just reports the pre-samples and post-samples required for the node graph at the current state, but somebody needs to be responsible for making sure that when we convert a frame to samples, we take the extra pre and post samples from the previous and next frame and include them in the signals we send into the processor, as well as cropping off the extra when they arrive. The processor doesn't need to know about this, it just takes in signals and outputs signals.
